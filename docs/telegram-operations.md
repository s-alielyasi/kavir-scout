# اجرای اپ تلگرام Kavir Scout

این راهنما برای کد پیاده‌شده است؛ طراحی اولیه در
[telegram-integration-plan.md](telegram-integration-plan.md) و وضعیت تحویل در
[telegram-implementation-status.md](telegram-implementation-status.md) ثبت شده‌اند.

## نصب و تنظیم

Python 3.11 یا جدیدتر و Chromium یا Google Chrome لازم است. روی دستگاه مقصد از ریشه مخزن اجرا کنید:

```bash
python -m venv .venv
```

سپس در Windows / PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -c requirements-tested.txt
```

در Linux/macOS همین دستور نصب وابستگی را با `./.venv/bin/python` اجرا کنید. در ادامهٔ
این راهنما نیز `python` را با مسیر مفسر محیط مجازی جایگزین کنید، مگر محیط را فعال کرده باشید.
اگر Google Chrome روی دستگاه نصب است، `BROWSER_CHANNEL=chrome` کافی است و
نصب Chromium همراه لازم نیست. در سیستم پشتیبانی‌شده، برای Chromium همراه
Playwright مقدار `BROWSER_CHANNEL` را خالی بگذارید و با مفسر محیط مجازی اجرا کنید:

```bash
python -m playwright install chromium
```

در Linux، پیش‌نیازهای سیستم مرورگر نیز باید نصب باشند. نصب Chromium همراه نسخهٔ
فعلی روی Ubuntu 20.04 پشتیبانی نمی‌شود؛ روی دستگاه آمادهٔ فعلی از Chrome استفاده
می‌شود. سایت واقعی برای اجرای تست‌های fixture لازم نیست.

کلیدهای [.env.telegram.example](../.env.telegram.example) را خصوصی در `.env`
تنظیم کنید. اگر `.env` دارید، کلیدها را ادغام کنید و فایل موجود را بازنویسی نکنید.
فقط در صورت نبود فایل خصوصی، می‌توانید نمونه را به `.env` کپی کنید. مقدارهای
exportشدهٔ محیط بر فایل اولویت دارند. هیچ مقدار حساس را به Git اضافه نکنید.

- `TELEGRAM_BOT_TOKEN`: توکن ربات مالک.
- `TELEGRAM_ALLOWED_USER_ID` و `TELEGRAM_ALLOWED_CHAT_ID`: هر دو شناسه عددی
  خصوصی و مثبت؛ نام کاربری جایگزین آن‌ها نیست. گروه، کانال، پیام ویرایش‌شده،
  پیام فورواردشده، ربات فرستنده و callback پشتیبانی نمی‌شوند.
- `TELEGRAM_PROXY_URL`: اختیاری؛ نشانی پراکسی HTTP(S) برای هر دو مسیر درخواست
  API و دریافت پیام تلگرام. خالی یعنی استفاده از رفتار پیش‌فرض SDK؛ تنظیمات
  گرافیکی پراکسی Linux خودکار خوانده نمی‌شوند. این مقدار فقط به کلاینت‌های
  تلگرام داده می‌شود و تنظیم پراکسی مرورگر فروشگاه را تغییر نمی‌دهد. نشانی
  شامل رمز را خصوصی نگه دارید. تغییر تنظیمات به شروع مجدد برنامه نیاز دارد.
- `DRY_RUN=true`: پیش‌فرض؛ حتی با پیدا شدن محصول، انتخاب، افزودن به سبد،
  تعیین تعداد و سفارش انجام نمی‌شود.
- `TARGET_QUANTITY=2`: تعداد تأییدشدهٔ مالک؛ پیش‌فرض کد و هر دو فایل نمونه نیز
  دو حلقه‌اند. تعداد چهار در پلن اولیه سابقهٔ طراحی است، نه تنظیم فعلی.
- `LIVE_CHECKOUT_APPROVED=false`: قفل انتشار مسیر سفارش. تا تأیید مراحل زنده،
  ممیزی ذخیره‌سازی، شرایط فروش و درگاه آن را تغییر ندهید. `DRY_RUN=false`
  بدون این تأیید، تنظیم معتبر محسوب نمی‌شود.
- `HEADLESS=false`: مرورگر نمایان برای مراحل انسانی. دسترسی امن به همان دستگاه
  لازم است؛ برنامه CAPTCHA یا صف را حل نمی‌کند.
- `BROWSER_CHANNEL`: مقدار خالی برای Chromium همراه Playwright؛ مقدار `chrome`
  برای Google Chrome نصب‌شده. روی Linux فعلی با Ubuntu 20.04، نصب Chromium
  همراه نسخهٔ بررسی‌شدهٔ Playwright پشتیبانی نمی‌شود؛ فایل خصوصی از Chrome
  نصب‌شدهٔ دستگاه استفاده می‌کند و نیازی به نصب Chromium همراه ندارد.
- `USER_DATA_DIR`: پروفایل اختصاصی؛ نمونهٔ تلگرام از `data/telegram_profile`
  استفاده می‌کند. پروفایل و کوکی را بین دستگاه‌ها کپی نکنید.

کد ملی و OTP تنظیم نیستند و داخل Config قرار نمی‌گیرند؛ فقط هنگام اجرا دریافت
می‌شوند. `NATIONAL_ID` قدیمی استفاده نمی‌شود و از فایل تنظیمات به محیط سراسری
فرایند کپی نمی‌شود. `.env` موجود توسط برنامه بازنویسی نمی‌شود.

```bash
python -m telegram_bot --check-config
python -m telegram_bot
```

بررسی تنظیمات اتصال تلگرام یا مرورگر را آغاز نمی‌کند. اجرای اپ فقط polling
تلگرام را آغاز می‌کند و تا دستور اجرا مرورگری باز نمی‌شود. `--test-inventory`
استثنای صریح برای شروع تست یک‌باره هنگام بالا آمدن برنامه است. ورودی قدیمی CLI یعنی
`python main.py` همچنان جریان مستقل خود را دارد و با اجرای آن، جریان مرورگری
شروع می‌شود؛ آن را برای راه‌اندازی ربات تلگرام استفاده نکنید.

## اجرای آماده در Linux

اسکریپت [run-telegram.sh](../run-telegram.sh) مفسر `.venv` همین پروژه را اجرا
می‌کند و از هر مسیر قابل فراخوانی است. ابتدا توکن و دو شناسهٔ `TELEGRAM_*` را در فایل
خصوصی `.env` کامل کنید؛ سپس از ریشهٔ پروژه:

```bash
./run-telegram.sh --check-config
./run-telegram.sh
```

این اسکریپت نصب یا اتصال تازه‌ای هنگام بررسی تنظیمات انجام نمی‌دهد. اجرای دوم
باید در ترمینال باز بماند؛ سرویس یا شروع خودکار سیستم نصب نمی‌کند. برای مرورگر
نمایان، آن را از نشست گرافیکی همین کاربر اجرا کنید و دستگاه را تا پایان کار
روشن و بیدار نگه دارید.

برای سناریوی ورود زودهنگام، برنامه را پیش از ساعت ۸ روشن کنید و در گفت‌وگوی
خصوصی ربات `/start` و سپس `/arm` بفرستید. پاسخ کد ملی و کد ورود را به پیام
درخواست مربوط reply کنید و هر مرحلهٔ دستی مرورگر را تکمیل کنید. پس از ورود،
`/status` باید آمادگی/انتظار شروع فروش را نشان دهد؛ پایش پیش از ۸ شروع نمی‌شود.
در ساعت ۸، بدون دستور تازه، زمان‌بندی جدول زیر آغاز می‌شود. در حالت `DRY_RUN`
پیداشدن موجودی فقط نتیجهٔ آزمایشی دارد و سفارشی ثبت نمی‌شود.

## تست یک‌باره، مستقل از ساعت

با `DRY_RUN=true` در گفت‌وگوی خصوصی `/test_inventory` بفرستید. ربات کد ملی و
در صورت نیاز OTP را از همان مسیر ورود دریافت می‌کند؛ پاسخ را به prompt مربوط
reply کنید. بعد از ورود، یک بار موجودی را با رعایت cooldown عادی تازه‌سازی
و بررسی می‌کند و با یکی از نتیجه‌های «موجود»، «ناموجود» یا «محصول پیدا نشد»
تمام می‌شود. حتی با موجودبودن محصول، هیچ انتخاب، تغییر تعداد یا سفارشی ندارد.

ساعت واقعی و تنظیمات بازهٔ روزانه تغییر نمی‌کنند. تست، تنها worker برنامه را
می‌گیرد؛ ورود هم‌زمان، کاربر نامجاز و marker سفارش حل‌نشده همچنان رد می‌شوند.
حالت سفارش زنده اجازهٔ این تست را نمی‌دهد. سقف کل تست ده دقیقهٔ زمان سپری‌شده
است؛ TTL هر ورودی کوتاه‌تر و مستقل است. `/status` حالت یک‌بررسی را نشان می‌دهد
و `/cancel` آن را متوقف می‌کند. CAPTCHA و مراحل دستی همچنان در مرورگر انجام می‌شوند.

برای شروع صریح همین تست همراه راه‌اندازی، ابتدا نمونهٔ فعلی را متوقف و اجرا کنید:

```bash
./run-telegram.sh --test-inventory
```

این فلگ پس از آماده‌شدن polling، prompt ورود می‌فرستد؛ راه‌اندازی عادی خودکار
اجرا نمی‌کند. برنامه پس از پایان تست برای دستور بعدی روشن می‌ماند. این تست
جای بررسی کامل الگوریتم زمان‌بندی صبح را نمی‌گیرد.

## استفادهٔ روزانه

`/start` معرفی و راهنماست. `/arm` فقط اجرای همان روز تهران را فعال می‌کند؛
پس از ۸:۱۵ رد می‌شود. اجرای دوم همزمان، worker یا درخواست ورودی تازه نمی‌سازد.
شروع مجدد برنامه، backlog قبلی تلگرام را کنار می‌گذارد و همیشه غیرفعال آغاز می‌شود.

به پیام درخواست کد ملی، همان پیام را reply کنید. پس از بررسی نشست، اگر ورود
لازم باشد کد پیامک درخواست می‌شود. کد هشت‌کاراکتری حساس به بزرگی حروف و کدهای
عددی سازگار با فرم پشتیبانی می‌شوند؛ فاصله داخلی کد پذیرفته نمی‌شود. پاسخ
به پیام دیگر، قدیمی، مصرف‌شده یا پس از مهلت قبول نمی‌شود. ورودی نامعتبر بازگو
نمی‌شود. حذف پیام ورودی در حد امکان انجام می‌شود؛ خطای حذف، روند ورود را خراب
نمی‌کند. خطای ارسال خود prompt، درخواست معلق را پاک و اجرا را متوقف می‌کند.

برای نشست از قبل واردشده، چون selector معتبر تطبیق هویت حساب تأیید نشده،
**تطبیق دستی حساب** درخواست می‌شود. فقط وقتی حساب مرورگر همان حساب موردنظر است
ادامه دهید؛ در صورت مغایرت `/cancel` بزنید و ورود صحیح را انجام دهید.

زمان‌بندی با `ZoneInfo("Asia/Tehran")` و تاریخ همان اجراست:

| بازهٔ تهران | فاصلهٔ حداقل شروع بررسی‌ها |
|---|---:|
| پیش از ۸:۰۰ | بدون پایش؛ آماده‌سازی ورود و انتظار |
| ۸:۰۰ تا پیش از ۸:۰۵ | ۵ ثانیه |
| ۸:۰۵ تا پیش از ۸:۱۰ | ۱۵ ثانیه |
| ۸:۱۰ تا پیش از ۸:۱۵ | ۳۰ ثانیه |
| از ۸:۱۵ | بدون بررسی/انتخاب تازه |

هر درخواست تا تکمیل درخواست قبلی منتظر می‌ماند. تأخیر سایت و cooldown می‌تواند
فاصله را بیشتر کند. نوبت‌های ازدست‌رفته با درخواست‌های پشت سر هم جبران نمی‌شوند.
نتیجه‌ای که بعد از پایان بازه برسد دور ریخته می‌شود. برگشت ساعت یا تغییر تاریخ
اجرا را متوقف می‌کند. یادآوری ۷:۵۵ فقط یک بار برای اجرای فعال با ورود ناقص است؛
به‌تنهایی اجرا یا خریدی را فعال نمی‌کند. این زمان‌بندی سیاست تنظیم‌شدهٔ مالک است،
نه تأیید جدید ساعت فروش سایت.

سفارش پذیرفته‌شده پیش از پایان بازه می‌تواند پس از ۸:۱۵، در مهلت محدود
`CHECKOUT_TIMEOUT_SECONDS` ادامه یابد؛ پس از پایان بازه سفارش تازه‌ای پذیرفته
نمی‌شود. مهلت تحویل درگاه جداگانه و محدود است. بستن اجباری فرایند، تضمین ذخیرهٔ
نهایی نشست یا لغو اقدام ثبت‌شده در سرور را نمی‌دهد.

`/status` وضعیت، زمان تهران، محصول، فاصله، آخرین نتیجه و مرحله قابل ادامه را
نشان می‌دهد؛ شامل کد ملی، OTP، کوکی یا لینک درگاه نیست. `/cancel` درخواست توقف
را فوراً ثبت می‌کند؛ وضعیت در زمان پاک‌سازی نیز قابل خواندن می‌ماند. توقف،
سفارشی را که سایت احتمالاً ثبت کرده لغو نمی‌کند.

خروجی‌های عمومی مانند `/start`، `/status`، نتیجهٔ دستورها و اعلان‌های اجرا
قابل کپی و فوروارد هستند. پیام‌های درخواست کد ملی/OTP و پیام حاوی دکمهٔ پرداخت
همچنان با `protect_content` ارسال می‌شوند. برای کپی وضعیت پس از ارتقا، دوباره
`/status` بفرستید؛ پیام قدیمی با ارسال نسخهٔ جدید تغییر نمی‌کند.

در مرحلهٔ دستی، به همان پیام `/resume` پاسخ دهید یا `/resume <checkpoint_id>`
فعلی را بفرستید. دستور بدون ارتباط با مرحلهٔ جاری کاری نمی‌کند. ادامه صرفاً
فرصت بررسی دوبارهٔ صفحه است؛ CAPTCHA، ۴۲۹، Retry-After و صف باید واقعاً رفع شوند.
تأیید Enter یا `/resume` به‌تنهایی وضعیت محدودیت HTTP را پاک نمی‌کند؛ پاسخ موفق
همان درخواست، پس از زمان انتظار، لازم است. در صورت لزوم مالک صفحه را دستی و
به‌صورت عادی بازخوانی می‌کند. اقدام نامطمئن سفارش دوباره کلیک نمی‌شود.

## درگاه و بازیابی سفارش

فقط HTTPS روی دامنه‌های تأییدشدهٔ `GATEWAY_HOSTS` پذیرفته می‌شود. درگاه قبلی یا
تب نامرتبط نتیجه سفارش جاری نیست و اجرا را متوقف می‌کند. popup باید متعلق به
صفحهٔ سفارش همین اجرا باشد. DOM و فیلدهای درگاه توسط اپ بررسی/پر نمی‌شوند.

لینک با دکمه «💳 پرداخت سفارش»، بدون preview و با protected content به همان
chat تنظیم‌شده فرستاده می‌شود. اپ تلگرام URL را در stdout، log یا
`payment_url.txt` نمی‌نویسد. خطای ارسال فقط ارسال همان لینک را با مهلت محدود
تکرار می‌کند؛ هرگز سفارش تازه نمی‌سازد. اگر چند بار ارسال شکست بخورد، ادامهٔ
مرحلهٔ مربوط فقط ارسال را تکرار می‌کند. مرورگر برای مهلت محدود تحویل باز می‌ماند.
«تحویل لینک» به معنی پرداخت موفق نیست. لینک ممکن است به POST، نشست یا دستگاه
وابسته باشد؛ قابل استفاده بودن روی تلفن هنوز باید به‌صورت زنده تأیید شود.

قبل از اولین انتخابِ بالقوه سفارش‌ساز، `data/order_attempt.json` به‌صورت atomic
و با fsync ثبت می‌شود. فقط run ID، تاریخ، وضعیت و تعیین تکلیف ثبت می‌شوند؛
اطلاعات هویتی، رمز، کوکی و URL داخل آن نیستند. marker پس از crash، لغو، تحویل
لینک یا عوض‌شدن روز خودکار حذف نمی‌شود. CLI نیز همین barrier را رعایت می‌کند.

ابتدا فرایند را متوقف و سفارش‌های موجود را در سایت بررسی کنید. سپس:

```bash
python -m telegram_bot --show-attempt
python -m telegram_bot --resolve-attempt no_order --attempt-run-id RUN_ID_FROM_OUTPUT
# فقط اگر سفارش موجود را بررسی و تعیین تکلیف کرده‌اید:
python -m telegram_bot --resolve-attempt order_exists --attempt-run-id RUN_ID_FROM_OUTPUT
```

این دستورها به توکن تلگرام نیاز ندارند و زیر قفل پروژه/پروفایل اجرا می‌شوند.
حین فعال‌بودن برنامه، تعیین تکلیف محلی اجرا نمی‌شود. شناسه باید دقیقاً همان
marker باشد؛ فایل خراب نیز خرید را مسدود می‌کند و نیازمند بررسی محلی است.
marker را صرفاً برای راه افتادن برنامه پاک نکنید. این مکانیزم تضمین exactly-once
در چند دستگاه یا در برابر تعیین تکلیف نادرست مالک نیست.

## محرمانگی، تست و انتشار

تلگرام کانال RAM-only یا سرتاسری برای ربات نیست؛ حذف پیام تضمین پاک‌شدن آن از
سرور، اعلان یا دستگاه‌ها نیست. Python نیز صفرکردن قطعی رشته‌ها در RAM را تضمین
نمی‌کند. برنامه مرجع کدهای مصرف‌شده را از broker و redactor حذف می‌کند و آن‌ها
را در وضعیت عمومی یا journal نمی‌گذارد.

در اپ تلگرام، debug احراز هویت/پروفایل و export جداگانه نشست خاموش‌اند. CLI
پشتیبان کوکی فقط همان پروفایل را دارد و LocalStorage/IndexedDB را کپی نمی‌کند.
پشتیبان قدیمی `data/storage_state.json` خودکار وارد نمی‌شود. خود پروفایل Chromium
همچنان روی دیسک است؛ رفتار واقعی ذخیره‌سازی، cache و autofill سایت باید پیش از
انتشار زنده روی دستگاه مقصد ممیزی شود. نبود raw identity روی دیسک صرفاً از این
تغییرات اثبات نمی‌شود. پروفایل، log و فایل‌های runtime را منتشر نکنید.

```bash
python -m unittest discover -v
python -m compileall -q main.py config.py kavirtire telegram_bot tests
git diff --check
```

تست‌های دائمی شامل fixture مرورگر، پیام‌های ساختگی تلگرام و ساعت قابل تزریق‌اند؛
توکن واقعی، پیامک، سفارش یا پرداخت واقعی ندارند. نسخه‌های بررسی‌شده در
`requirements-tested.txt` آمده‌اند. نتیجهٔ fixture تأیید DOM پشت ورود یا امنیت
وابستگی‌ها در پایگاه CVE نیست.

روی Linux آمادهٔ فعلی برای تست کامل با Chrome نصب‌شده اجرا کنید:

```bash
TEST_BROWSER_CHANNEL=chrome ./.venv/bin/python -m unittest discover -v
```

این متغیر فقط مرورگر fixture را انتخاب می‌کند؛ تست‌ها فایل خصوصی `.env` را
نمی‌خوانند و درخواست‌های صفحهٔ بدون route ساختگی مسدودند. ردیف‌های چهارحلقه‌ای
تست، دادهٔ ساختگی مستقل از پیش‌فرض دوحلقه‌ای برنامه‌اند.

پاسخ‌گویی واقعی `/start` و `/status` و کپی خروجی توسط مالک تأیید شده است.
برای تکمیل مراحل ۱۵ و ۱۶، ورود، توقف در جریان واقعی، dry-run موجودی، ممیزی
دادهٔ ذخیره‌شده و تأیید شرایط تعداد هدف روی دستگاه مقصد باقی مانده‌اند؛ checkout
واقعی و تحویل قابل استفادهٔ درگاه نیز به درخواست صریح مرتبط نیاز دارند.
هدف فعلی دو حلقه است؛ شرایط جاری سایت باید در همان
اجرای واقعی بررسی شود. برنامه سقف را دور نمی‌زند و تعداد را خودسرانه عوض نمی‌کند.
